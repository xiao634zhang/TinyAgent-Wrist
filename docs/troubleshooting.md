# 踩过的坑：按证据定位

| 观察 | 优先检查 | 下一步 |
|---|---|---|
| 服务器没有成功回执 | 电脑网络、HTTPS错误、发送入口 | 检查本地异常类型，不连续重发 |
| 服务器成功，打开ntfy后才补出消息 | ntfy后台网络/耗电、实时推送、网络切换 | 确认ntfy本身的后台权限，熄屏复测 |
| App列表有消息，系统通知没有 | 前台主题、静音、最低优先级、系统通知权限/通道 | 先回桌面；检查过滤条件 |
| 系统通知有，手环没有 | Keep监听权限、来源选择、设备连接、勿扰时段 | 打开配套App确认连接，再后台测试 |
| 手环只显示部分内容 | 设备字数与显示能力 | 手机查看完整消息，缩短max_chars |

## 1. 常驻服务通知 ≠ 独立消息通知

“正在监听通知”只代表服务呈现了常驻通知，不证明当前订阅连接有效；Keep也不一定转发这类持续通知。要找每条测试消息的独立系统通知。

实测遇到“常驻通知还在、打开App才补收”。ntfy当时为“智能控制后台耗电”，改为“允许后台耗电”后，熄屏测试在系统通知栏和手环均收到。这个前后对照支持后台限制是重要原因，但不能证明其他手机上的同类问题都由此引起。

## 2. 打开主题反而看不到系统通知

ntfy Android 1.25.2在主题详情可见时跳过该主题的通知；打开主题还会清理已有弹出通知。于是“我在App里看到了”与“Android曾产生独立通知”是两件事。

测试应先回桌面、熄屏，先查看系统通知栏和手环，再打开ntfy。不要把手机一整天禁止打开ntfy当作解决办法。源代码：[通知判定](https://github.com/binwiederhier/ntfy-android/blob/v1.25.2/app/src/main/java/io/heckel/ntfy/msg/NotificationDispatcher.kt)、[详情页生命周期](https://github.com/binwiederhier/ntfy-android/blob/v1.25.2/app/src/main/java/io/heckel/ntfy/ui/DetailActivity.kt)。

## 3. 默认优先级被继承设置过滤

订阅曾继承最低提醒等级5，而发送的是4，导致有消息却不提醒。按需将这个主题最低等级设为3；不要为了测试改全局所有主题。系统通知通道也有独立设置。见[ntfy官方手机说明](https://docs.ntfy.sh/subscribe/phone/)。

## 4. 原生事件、手动样本、真正送达不能混为一谈

曾出现完成回复没有对应发送记录；另一些原生Stop又能正常触发。显式完成/询问兜底由代理在输出前执行，缓解原生事件缺失，但需要会话载入规则。安装命令成功不能替代信任审查；服务器成功不能替代手机/手环回执。

## 5. 自动权限审批和输入框建议造成噪声

原始PermissionRequest在自动审核流程里也会出现，不能可靠认定为“需要用户操作”。默认静音这类事件；需要用户回答的问题仍发送正文和选项。输入框预测建议可能产生Stop，因此按线程分类和suggestion载荷过滤，而不是过滤回复中所有“建议”字样。

## 6. USB、模拟器、中文输入与旧XML

只有模拟器时，不应“连接成功”后误操作模拟器。默认排除模拟器并使用USB身份核验，明确指定serial时由调用者负责选择。线缆需支持数据。点击和滑动用新截图的坐标。中文输入法可能重排ASCII；`adb input text`不直接支持中文。动态页uiautomator可能失败，不能读取旧文件当作新状态。

## 7. IPv4线路偶发超时

实测曾有电脑代理IPv4路径超时而同域名IPv6可达。脚本仅对未认证的 `ntfy.sh` 连接失败尝试IPv6地址，保留域名、SNI及TLS校验；不会使用 `-k`，不会对HTTP429等明确拒绝换线路重发。DNS备用只查询公开域名，结果有过期缓存。

带 `NTFY_TOKEN` 时关闭curl备用，避免令牌进入子进程参数；认证请求只使用Python HTTPS。网络结果不明确时仍可能重复投递，不能宣称严格一次送达。不要为排查关闭系统安全保护或泄露代理凭据。

## 8. 单次成功不能代表长期稳定

至少补做长时间熄屏、Wi-Fi/移动网络切换、断网恢复和Keep连接恢复。请记录阶段性结果，不把一次手环震动写成“永久稳定”。当前没有自动化手环端送达确认。
